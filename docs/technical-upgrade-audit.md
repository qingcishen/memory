# Cyber Memory 技术升级审查

> 审查日期：2026-07-28  
> 审查范围：项目结构、认知架构、记忆与检索、状态系统、对话编排、评测体系、工程质量与后续技术路线。  
> 本文是架构与技术方向审查，不包含代码修改。

## 1. 执行摘要

Cyber Memory 已经不是普通的“对话写入向量库，再做 top-k 检索”的记忆 RAG。

项目目前具备：

- 长期记忆提取；
- 重要性、衰减与访问强化；
- 记忆冲突与 `superseded_by` 历史链；
- ACT-R 风格激活计算；
- 情绪一致性与定向心情门控；
- 关系、情绪、欲望、身体与生活状态；
- 预期记忆与主动消息；
- 故事线、关系叙事与 session thread；
- 多模态记忆与角色外观；
- 知识图谱；
- Telegram、飞书和 Discord 等渠道；
- trace、成本统计、记忆基准、对话评测和消融实验。

从功能广度看，项目已经明显超过一般的开源 AI companion。不过，当前的主要瓶颈也已经从“缺少功能”转变成：

> 系统拥有大量看起来像智能的机制，但这些机制仍主要依赖规则、Prompt 拼装和 JSON 状态协作，尚未形成统一、可学习、可验证的认知架构。

下一轮突破不应继续增加更多穿搭、生活、渠道或状态字段，而应把项目从“功能丰富的 AI 伴侣应用”升级为：

> 具备统一认知内核、时态信念、事件溯源、证据决策和数据学习能力的长期智能体系统。

## 3. 核心架构诊断

### 3.1 当前回复链路

当前一轮回复大致经过：

```text
用户消息
  ↓
场景识别
  ↓
情绪标签
  ↓
关系阶段
  ↓
身体状态
  ↓
欲望与对话目标
  ↓
结构化计划
  ↓
记忆召回
  ↓
故事线、画像与世界状态
  ↓
Prompt 组装
  ↓
LLM 回复
  ↓
连贯性修复
  ↓
人类化后处理
  ↓
历史、记忆与多种状态异步更新
```

每个模块单独看都有合理性，但整体仍然属于专家规则系统：

- 情绪模块输出标签；
- 行为策略根据标签生成指令；
- 关系阶段继续覆盖行为；
- 身体状态再次覆盖行为；
- 结构化计划决定本轮态度和形式；
- 多个模块最终被转换成自然语言 Prompt；
- 最后的冲突协调主要由回复模型完成。

这意味着系统没有共享一个明确的世界模型，也没有统一的冲突解决机制。

### 3.2 典型冲突

以下问题当前主要依靠 Prompt 和局部优先级解决：

- 关系紧张时用户生病，应该优先关心还是保持别扭；
- 角色想被关注，但用户明确表示很忙，是否继续主动联系；
- 用户以前讨厌香菜，最近说“现在觉得还可以”，这是偏好改变还是临时例外；
- 角色心情低落时召回负面记忆，是合理的情绪一致性还是系统主动制造矛盾；
- story、desire、relationship、prospective 同时要求在本轮出现时，谁应该获得优先级；
- 多个模块提供互相矛盾的回复长度、语气、内容和行为建议时，最终由谁裁决。

随着模块继续增加，这种设计会逐渐变成一个 Prompt 控制系统：行为难以预测，调节一个模块可能使另一个模块退化。

消融实验中多项机制关闭后得分反而上升，与这一问题高度一致。

## 4. 记忆与检索审查

### 4.1 已有优势

现有记忆系统的优点包括：

- 不是无差别存储所有对话；
- `fact_core` 与主观 `narrative` 分离；
- `fact_core` 有不可改写红线；
- 记忆具备重要性、情绪、访问记录和置信度；
- 当前事实与旧版本通过 supersede 链分离；
- 支持显式回查历史偏好；
- 支持向量与关键词双路召回；
- 支持 RRF、启发式、LLM 与 activation reranker；
- 支持访问强化和遗忘参数拟合；
- 支持关系里程碑与情绪一致性。

这些能力已经构成较完整的记忆工程基础。

### 4.2 当前上限

现有 memories 本质上仍是一组带元数据的文本记录。它可以很好地回答“哪些记忆与当前问题相关”，但不擅长严格回答：

- 某件事在什么时间范围内成立；
- 某个结论来自用户明确陈述、助手推断还是模型猜测；
- 两条记忆是互相矛盾、临时例外还是事实变化；
- 当前事实的置信度为什么是这个数；
- 没有充分证据时系统应该回答“不知道”还是进行弱推测；
- 多条低置信度证据能否共同支持一个高置信度结论；
- 助手自己说过的话是否被错误地当成用户事实。

下一步不应继续只强化文本召回，而应在文本记忆之上增加结构化信念层。

## 5. 评测体系审查

项目已经完成了非常关键的转变：开始使用真实管线 benchmark、trace、成本统计和消融实验。这个方向正确，但现有数据仍不足以支撑所有架构结论。

### 5.1 记忆基准区分度不足

当前公开结果：

| 配置 | Overall | Recall@5 | MRR | p95(ms) | Cost/run |
|---|---:|---:|---:|---:|---:|
| heuristic-vector | 0.92 | 1.00 | 0.9625 | 5152 | $0.0172 |
| heuristic-hybrid | 0.92 | 1.00 | 0.9625 | 6831 | $0.0172 |
| llm-hybrid | 0.90 | 1.00 | 0.9750 | 13941 | $0.0194 |
| activation-hybrid | 0.88 | 1.00 | 1.0000 | 3429 | $0.0174 |

所有配置的 Recall@5 都达到 1.00，说明当前 50 道题已经接近饱和，无法有效区分后续检索算法。

activation-hybrid 的 MRR 最好，但端到端 Overall 从 0.92 降到 0.88。选择它作为默认配置优化了“正确记忆排第几”，却牺牲了“最终回答是否正确”。

这暴露出一个重要问题：

> 检索排序指标与最终任务指标尚未完全对齐。

后续默认配置不应由单一 MRR 决定，而应综合：

- 最终回答正确率；
- 矛盾率；
- 拒答准确率；
- Recall 与 MRR；
- 延迟；
- 成本；
- 隐私与跨角色泄漏风险。

### 5.2 延迟实验可能含有较大运行噪声

activation-hybrid 逻辑更复杂，却测出最低 p95。这个结果可能成立，但也可能受到以下因素影响：

- Supabase 网络波动；
- embedding 或模型冷启动；
- 不同配置的运行顺序；
- 数据库缓存；
- 样本量不足；
- 端到端耗时混入回答模型延迟。

后续应拆分记录：

```text
embedding latency
vector recall latency
keyword recall latency
fusion latency
rerank latency
reinforcement write latency
answer generation latency
```

实验应随机化配置运行顺序，重复运行并报告：

- median；
- p95；
- 标准差；
- bootstrap 置信区间。

### 5.3 消融实验仍需增强统计可信度

当前消融显示：

| 机制 | 开启分 | 关闭分 | Δ | 当前结论 |
|---|---:|---:|---:|---|
| monologue | 2.99 | 3.49 | -0.51 | 有害，删除 |
| behaviorPolicy | 2.99 | 3.49 | -0.51 | 有害，删除 |
| moodGating | 2.99 | 3.32 | -0.33 | 无法证明增益 |
| reconsolidation | 2.99 | 3.13 | -0.15 | 无法证明增益 |
| narration | 2.99 | 2.97 | +0.01 | 无法证明增益 |
| story | 2.99 | 3.19 | -0.20 | 无法证明增益 |
| desire | 2.99 | 3.28 | -0.29 | 无法证明增益 |

这些结果至少证明：多个机制尚未形成稳定的端到端收益。

**各维度拆解（baseline 2.99/5）**

| 维度 | 分值 | 判断 |
|---|---:|---|
| no_breaking | 3.47 | 相对最稳 |
| memory_consistency | 3.20 | 中等，已有记忆框架支撑 |
| persona_stability | 2.80 | 偏低，多模块互相覆盖人设 |
| emotional_fitness | 2.73 | 最弱 — F2 情绪标签准确率 63.7% 直接导致 |
| naturalness | 2.73 | 最弱 — prompt 段落过多，LLM 在多重约束下生成机械 |

情绪契合与自然度并列最低。前者的直接根因是 F2 规则分类器天花板（规则最多 65%），后者与 prompt 复杂度正相关——两者均有清晰升级路径（见第 7 节）。

但固定使用 ±0.5 作为 judge 噪声阈值比较粗。更可靠的消融应加入：

- 同一输出由多个 judge 独立评分；
- judge 不知道输出来自哪种配置；
- 同一剧本使用多个随机种子；
- 优先使用成对比较，而不仅是绝对评分；
- 对分差计算 bootstrap 置信区间；
- 为每个机制建立专属场景集。

不同机制还需要不同的评价尺度。例如，reconsolidation 的价值不应主要由普通对话自然度判断，而应通过“冲突发生—关系修复—时间过去—再次回忆”的长期轨迹题判断。

### 5.4 基础模型是最大天花板（我方补充）

当前回复模型为 GLM-4-Flash（廉价高速），E3 v2 baseline 2.99/5 很大程度是底层模型能力上限，而非单独某个机制的问题。

| 模型路径 | 预期对话分提升 | 成本增量估算 |
|---|---|---|
| GLM-4-Flash → Claude Haiku 4.5 | +0.8~1.2 pts | ~5x/回复 |
| Claude Haiku 4.5 → Sonnet 5 | 再 +0.5~0.8 pts | ~15x |
| 当前模型 + 针对性 LoRA 微调 | +0.5~0.8 pts | 一次性训练成本 |
| Hybrid：Claude 回复 + GLM 提取/judge | 最优性价比 | 可控 |

建议在删除 monologue + behaviorPolicy 并重跑 E3 后，以同一剧本集对比 GLM-4-Flash vs Claude Haiku 4.5，直接量化模型升级的 Δ。微调数据来源：已有对话轨迹 + E2 judge 4.5+ 分正例。

### 5.5 情绪信号存在误差级联

近期情绪推断准确率已有明显提升，但仍不足以成为多个下游模块的绝对控制信号。

当前情绪判断会进一步影响：

- 行为策略；
- 记忆门控；
- 欲望；
- 关系状态；
- 主动消息；
- 回复采样参数。

一旦上游标签判断错误，误差会沿整条链路扩散。

情绪推断应从单一离散标签升级为带置信度的概率输出：

```js
{
  distribution: {
    calm: 0.16,
    disappointed: 0.51,
    hurt: 0.25,
    jealous: 0.08
  },
  evidence: [],
  confidence: 0.61,
  target: "user | external | self | unknown"
}
```

下游模块根据置信度决定：

- 强控制；
- 软提示；
- 不采用该信号。

### 6.1 Orchestrator 已接近 God Object

当前 Orchestrator 同时负责：

- 初始化依赖；
- 加载状态；
- 场景判断；
- 情绪与关系计算；
- 对话计划；
- 记忆检索；
- Prompt 装配；
- 模型调用；
- 流式输出；
- 连贯性重试；
- 回复后处理；
- 历史记录；
- 图片触发；
- trace；
- 异步状态更新；
- 主动消息；
- 维护任务。

继续向这个类增加机制，会使局部修改越来越容易影响整条回复链。

建议将一次对话显式建模为七阶段流水线：

```text
Perceive
  ↓
Interpret
  ↓
Retrieve
  ↓
Deliberate
  ↓
Compose
  ↓
Validate
  ↓
Commit
```

每个阶段都应具备稳定的结构化输入输出：

```js
TurnContext
Interpretation
EvidencePack
Decision
Draft
ValidationResult
CommittedEvents
```

这样才能支持：

- 确定性回放；
- 分阶段 trace；
- 局部缓存；
- 并行执行；
- 独立降级；
- 消融实验；
- 离线数据生成；
- 模块替换；
- 状态提交事务化。

### 6.2 状态提交存在一致性风险

当前回复完成后，多种更新采用异步或 fire-and-forget 方式执行。这样可以降低用户感知延迟，但也可能产生：

- 回复已经发送，记忆没有写入；
- 关系状态写入成功，情绪状态失败；
- history 已记录，事件处理重试后重复更新；
- 图片、故事和关系状态看到不同版本的世界；
- 进程退出导致部分后台任务丢失。

已有 jobs、幂等和事件 ID 基础，但下一步应统一进入 commit 阶段，通过事件日志和幂等消费者更新投影视图。

## 7. 六个核心突破方向

### 7.1 从记忆条目升级为时态信念系统

这是最值得优先建设的核心能力。

建议在文本记忆之上增加 Belief 层：

```js
Belief {
  subject
  predicate
  object
  validFrom
  validTo
  epistemicStatus
  confidence
  provenance
  contradictions
  observationCount
  lastConfirmedAt
}
```

示例：

```text
用户 — 喜欢 — 香菜
validFrom: 2026-07-10
confidence: 0.72
provenance: [memory-123, turn-882]
supersedes: belief-37
```

它需要支持：

- 时态有效性；
- 来源追踪；
- 事实、推断和猜测分离；
- 冲突证据累积；
- 置信度更新；
- 不知道判断；
- 偏好变化与临时例外区分；
- 助手陈述与用户陈述隔离。

这不是普通知识图谱，而是：

> 带时间、来源和不确定性的个人信念数据库。

### 7.2 建立事件溯源式状态系统

当前关系、情绪、欲望和生活状态主要保存当前快照，部分模块另存历史。

更强的设计应是：

```text
原始对话或外部事件
  ↓
认知事件
  ↓
状态转移
  ↓
当前投影视图
```

例如：

```js
{
  type: "USER_REPAIRED_CONFLICT",
  evidenceTurnId: "turn-123",
  confidence: 0.84,
  effects: {
    tension: -0.18,
    trust: 0.04,
    repairDebt: -0.20
  }
}
```

当前状态由事件流投影产生，而不是由多个模块分别修改。

收益包括：

- 解释“为什么现在生气”；
- 回放任意关系历史；
- 修正错误推断；
- 运行反事实实验；
- 比较不同状态转移算法；
- 避免半更新状态；
- 为未来训练状态转移模型积累数据。

### 7.3 从规则优先级升级为约束式决策器

当前 structured plan 已经是决策层的雏形，但仍主要依靠启发式规则。

建议把本轮回复策略正式表示为候选行为：

```js
ActionCandidate {
  intent
  utility
  risks
  evidence
  constraints
  expectedStateChange
}
```

候选行为可以包括：

- 安慰；
- 追问；
- 回忆旧事；
- 分享角色生活；
- 保持沉默；
- 调情；
- 道歉；
- 提供建议；
- 安全阻断。

统一效用可以表达为：

```text
utility =
  relationship benefit
  + user need satisfaction
  + persona consistency
  + continuity
  + information gain
  - interruption cost
  - safety risk
  - repetition penalty
  - hallucination risk
```

这会使决策：

- 可 trace；
- 可解释；
- 可消融；
- 可离线比较；
- 可逐步学习。

### 7.4 将检索升级为证据预算分配

当前检索主要回答“哪些记忆相关”。更高级的问题应该是：

> 在有限上下文预算中，哪些证据最值得占用 token？

应统一考虑：

- 长期记忆；
- 最近对话；
- 当前关系状态；
- 用户画像；
- 故事线；
- 预期记忆；
- 角色生活状态；
- 世界状态。

每条证据可以包含：

```js
{
  relevance,
  necessity,
  confidence,
  freshness,
  contradictionRisk,
  tokenCost,
  source
}
```

选择目标可以表示为：

```text
maximize:
  answer coverage
  + continuity
  + personalization
  - redundancy
  - token cost
  - contradiction risk
```

这比继续添加单独的 reranker 更能解决 Prompt 持续膨胀的问题。

### 7.5 建设困难的长期智能体评测

下一套 benchmark 不应继续增加简单事实题，而应覆盖：

- 1000 条噪声记忆中的目标召回；
- 同名人物消歧；
- 偏好的临时例外；
- 多次反复变化的事实；
- 模糊时间表达；
- 错误记忆纠正；
- 助手编造内容不得反向成为用户事实；
- 多角色之间绝对隔离；
- 跨渠道记忆继承；
- 数周跨度的承诺兑现；
- 关系修复后的旧事件重新解释；
- Prompt 注入诱导记忆泄漏；
- 用户要求删除后不可再召回；
- 没有证据时稳定拒答。

建议增加以下指标：

- Belief accuracy；
- Temporal consistency；
- Contradiction rate；
- Abstention precision/recall；
- Provenance correctness；
- Privacy leakage；
- Long-horizon commitment success；
- State calibration；
- Cost-adjusted quality。

### 7.6 从人工规则调参走向数据驱动学习

现阶段不建议直接训练大型模型。更实际的路径是：

1. 所有推断输出特征、证据和置信度；
2. 记录最终用户反馈信号；
3. 构建离线训练集；
4. 先训练小型、可解释模型；
5. 与规则系统做 shadow 对比；
6. 达到门槛后逐步替换规则。

优先学习的模块：

- 记忆重要性；
- 情绪与需求概率；
- 主动消息发送价值。

后续可学习：

- 检索权重；
- 行为选择；
- 状态转移幅度；
- 遗忘参数。

这一步将建立真正的数据飞轮，让系统具备“使用越久越好”的能力。

### 7.7 情绪分类器 ML 升级（我方补充，针对 emotional_fitness 2.73）

当前 `inferEmotionLabelRaw` 是规则集，F2 准确率 63.7%，天花板约 65%。原因：

- 同一 `valence/warmth/attention` 快照组合，不同标注者给出不同标签（标注集内部一致性不足）
- 自然语言语义无法被规则完整捕捉（"发现牛肉面里挺香" 被标为开心，规则层看不出来）
- GLM-4-Flash zero-shot 分类 57%，不优于规则，因强偏 "平静"

**升级路径**：

1. 扩充标注集至 ≥300 条 `goldLabel`（现有 204 条 `initialLabel`，缺口 96 条）
2. 用 `text-embedding-3-small` 把 `(state_snapshot + userText)` 嵌入向量
3. 训练 8 分类 k-NN 或轻量 MLP（输入：向量 + valence/warmth/attention 数值特征）
4. 用现有 `eval-emotion-labels.js` 脚本评测，目标 ≥ 85%

预期：嵌入方法通常可达 82~90%，因为它能捕捉语义而规则不能。达标后替换 `inferEmotionLabelRaw`，上游所有依赖情绪标签的模块（行为、采样、resonance）随之受益，emotional_fitness 维度应显著提升。

## 8. 建议的 v4 主线

建议下一版本定义为：

> **v4 Cognitive Core：从机制堆叠到统一、可解释、可学习的认知内核。**

### 8.1 第一阶段：架构收敛

目标：

- 将 Orchestrator 拆成七阶段流水线；
- 定义统一 `TurnContext`；
- 所有阶段输出结构化结果；
- 状态更新统一进入 commit 阶段；
- 回复链支持确定性 replay；
- 拆分 UI server 和渠道公共层；
- 给核心数据结构增加 Zod schema 与渐进类型检查。

验收：

- 同一个 trace 可以离线重放；
- 每个阶段可以独立替换和消融；
- 回复生成前不提交长期状态；
- commit 失败可以安全重试；
- 重试不会重复写入。

### 8.2 第二阶段：Belief Engine

目标：

- 在现有 memory 上增加结构化 belief 投影；
- 支持时态、置信度、来源和冲突；
- 实现 `current / history / unknown` 查询；
- 回答事实问题时保留内部 provenance；
- 保留文本记忆用于情感、情节与模糊联想。

建议的系统分工：

```text
Belief graph
  负责事实、偏好、关系、时间和承诺

Episodic memory
  负责经历、场景、情绪和叙事

Semantic retrieval
  负责模糊联想和候选发现
```

### 8.3 第三阶段：决策内核

目标：

- 使用候选行为替换大量直接规则；
- 定义硬约束与软目标；
- 记录每个候选行为的得分与证据；
- 通过 paired evaluation 调整效用；
- 将 story、desire、prospective 统一视为行为动机，而不是直接向 Prompt 注入要求。

### 8.4 第四阶段：困难评测与在线学习

目标：

- 增加 adversarial long-horizon benchmark；
- 使用多 judge、盲测、重复采样和置信区间；
- 建立用户反馈事件；
- 从重要性、情绪概率和主动发送价值开始学习；
- 保留规则系统作为 fallback 与安全边界。

## 9. 暂不建议继续投入的方向

短期内不建议优先开发：

- 新聊天渠道；
- 更多穿搭细节；
- 更多生活状态字段；
- 更多离散情绪标签；
- 新的 LLM reranker；
- 更多直接拼入 system prompt 的模块；
- 没有专属 benchmark 的心理学机制；
- 全量 TypeScript 重写；
- 直接训练或微调大型模型。

这些方向可以增加功能展示与代码量，但不能解决当前认知协调、评测区分度和数据学习能力不足的问题。

## 10. 推荐的第一个落地切片

如果只选择一个兼具技术含量、产品价值和可控范围的切片，建议优先实现：

> **Temporal Belief Engine v1：带时间、来源、冲突和置信度的用户信念层。**

第一版只覆盖四类信息：

1. 身份事实；
2. 稳定偏好；
3. 时间事件；
4. 承诺。

建议交付：

1. `beliefs` 与 `belief_evidence` 数据模型；
2. 从 memory 投影 belief；
3. 冲突与更新算法；
4. `current / history / unknown` 查询接口；
5. provenance 调试视图；
6. 至少 50 个困难时态与冲突测试；
7. 与现有纯文本记忆召回的端到端对比。

完成这个切片后，项目定位可以从：

> 类人记忆系统

升级为：

> 具备时态信念、情节记忆和关系状态的长期 AI 认知基础设施。

## 11. 建议优先级

> 综合 Codex 架构分析与实测数据（E3 v2、F2 baseline、per-rubric 得分）更新。

## 12. 最终结论

Cyber Memory 当前不缺功能，也不缺概念。它真正缺少的是一个能够统一已有机制的认知核心。

下一阶段的技术含量不应通过“再增加多少模块”体现，而应通过以下能力体现：

- 能区分事实、推断与未知；
- 能表达事实随时间变化；
- 能说明每个结论来自哪里；
- 能回放状态为什么发生变化；
- 能在多个动机之间做可解释决策；
- 能用困难评测证明机制有效；
- 能从真实数据中逐步替代人工参数。

当这些能力形成闭环后，项目才会从一个功能丰富的 AI 伴侣工程，升级成真正具有研究价值、工程壁垒和平台潜力的长期智能体认知系统。
